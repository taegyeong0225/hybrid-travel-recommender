# 11주차 회원가입 로직 해결

## 문제 원인

회원가입 API 엔드포인트(`/auth/signup`)에서 응답을 반환할 때 직렬화 오류가 발생했습니다.

### 근본 원인

**backend/app/schemas.py**의 `User` 스키마가 `favorites`와 `visits` 관계 필드를 포함하고 있었습니다:

```python
class User(UserBase):
    id: int
    created_at: datetime
    favorites: List[FavoritePlace] = []  # 문제!
    visits: List[VisitedPlace] = []      # 문제!
```

**backend/app/auth.py**의 `signup` 엔드포인트에서:

```python
@router.post("/signup", response_model=schemas.User)
def signup(user: schemas.UserCreate, db: Session = Depends(get_db)):
    # ...
    created_user = crud.create_user(db=db, user=user, hashed_password=hashed_password)
    return schemas.User.from_orm(created_user)
```

### 문제 발생 메커니즘

1. `crud.create_user()`는 새로운 User 객체를 생성하고 데이터베이스에 저장합니다
2. 이 시점에서 `created_user` 객체는 `favorites`와 `visits` 관계를 **로드하지 않은 상태**입니다
3. `schemas.User.from_orm(created_user)`를 호출하면 Pydantic이 `favorites`와 `visits` 필드를 직렬화하려고 시도합니다
4. SQLAlchemy의 lazy loading으로 인해 관계가 로드되지 않아 오류가 발생하거나, 로드하더라도 불필요한 추가 쿼리가 발생합니다

### 왜 문제가 되는가?

- **성능 문제**: 관계를 로드하기 위해 추가 데이터베이스 쿼리가 필요 (N+1 쿼리 문제)
- **불필요한 데이터**: 회원가입 시점에는 favorites와 visits가 비어있으므로 응답에 포함할 필요가 없음
- **관심사의 분리**: 회원가입과 사용자 프로필 조회는 다른 목적의 API입니다

## 해결 방안

### 선택한 방법: 회원가입 전용 응답 스키마 생성 (방법 3)

관계 필드를 포함하지 않는 별도의 `UserResponse` 스키마를 생성했습니다.

#### 1. schemas.py 수정

```python
# 기존 User 스키마는 유지 (관계 포함, /auth/me 등에서 사용)
class User(UserBase):
    id: int
    created_at: datetime
    favorites: List[FavoritePlace] = []
    visits: List[VisitedPlace] = []

    class Config:
        from_attributes = True

# 새로운 UserResponse 스키마 추가 (관계 제외, 회원가입용)
class UserResponse(UserBase):
    id: int
    created_at: datetime

    class Config:
        from_attributes = True
```

#### 2. auth.py 수정

```python
@router.post("/signup", response_model=schemas.UserResponse)  # User → UserResponse
def signup(user: schemas.UserCreate, db: Session = Depends(get_db)):
    db_user = crud.get_user_by_username(db, username=user.username)
    if db_user:
        raise HTTPException(status_code=400, detail="Username already registered")

    hashed_password = get_password_hash(user.password)
    created_user = crud.create_user(db=db, user=user, hashed_password=hashed_password)

    return schemas.UserResponse.from_orm(created_user)  # User → UserResponse
```

### 장점

1. **성능 개선**: 불필요한 관계 로딩 쿼리 제거
2. **명확한 API 설계**: 각 엔드포인트의 목적에 맞는 응답 구조
3. **유지보수성**: 기존 코드 영향 최소화 (User 스키마는 다른 곳에서 계속 사용 가능)
4. **확장성**: 향후 회원가입 응답에 추가 필드가 필요하면 UserResponse만 수정

### 다른 고려했던 방법들

#### 방법 1: crud.py의 create_user에서 관계를 로드

```python
def create_user(db: Session, user: schemas.UserCreate, hashed_password: str):
    db_user = models.User(...)
    db.add(db_user)
    db.commit()
    db.refresh(db_user)
    # 관계를 명시적으로 로드
    db_user.favorites
    db_user.visits
    return db_user
```

**단점**: 모든 create_user 호출에서 불필요하게 관계를 로드

#### 방법 2: auth.py에서 관계를 명시적으로 로드

```python
def signup(...):
    created_user = crud.create_user(...)
    # 관계 로드
    created_user.favorites
    created_user.visits
    return schemas.User.from_orm(created_user)
```

**단점**: 빈 리스트를 로드하기 위한 불필요한 코드

## 추가 문제: API 경로 404 오류

### 문제 상황

위의 스키마 문제를 해결한 후에도 회원가입 API 호출 시 404 오류가 발생했습니다:

```bash
curl -X POST http://localhost:8000/api/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"username": "testuser", "name": "Test User", "password": "test1234"}'
# 응답: {"detail":"Not Found"}
```

### 원인 분석

**backend/app/main.py**에서 라우터를 등록할 때 prefix가 없었습니다:

```python
# 문제 코드
app.include_router(auth_router)
app.include_router(user_places_router)
```

하지만 프론트엔드(frontend/src/Signup.jsx)는 `/api` prefix를 포함한 경로로 요청을 보냈습니다:

```javascript
const response = await fetch('/api/auth/signup', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ name, username, password }),
});
```

**결과**: 백엔드는 `/auth/signup`을 등록했지만, 프론트엔드는 `/api/auth/signup`을 호출하여 경로 불일치 발생

### 해결 방법

**backend/app/main.py**의 라우터 등록 부분을 수정하여 `/api` prefix를 추가했습니다:

```python
# 수정된 코드 (main.py:64-65)
app.include_router(auth_router, prefix="/api")
app.include_router(user_places_router, prefix="/api")
```

### 결과

이제 다음 경로들이 정상 작동합니다:
- `/api/auth/signup` (회원가입)
- `/api/auth/login` (로그인)
- `/api/auth/me` (현재 사용자 정보)
- `/api/user/{user_id}/favorites` (즐겨찾기)
- `/api/user/{user_id}/visits` (방문 장소)

### 교훈

프론트엔드와 백엔드의 API 경로는 반드시 일치해야 합니다. 특히:
- Nginx 등의 리버스 프록시를 사용하는 경우 경로 매핑 확인 필요
- 프론트엔드의 API 호출 경로와 백엔드 라우터 등록 시 prefix 일치 확인
- 개발 초기에 API 경로 컨벤션을 명확히 정의 (예: `/api/v1/...`)

## 추가 문제 2: Docker 환경에서 Nginx 프록시 설정 오류

### 문제 상황

백엔드에서 직접 curl로 테스트하면 정상 작동하지만, 웹사이트(Docker 환경)에서 회원가입을 시도하면 여전히 404 오류가 발생했습니다.

```bash
# 백엔드 직접 호출 - 성공
curl -X POST http://localhost:8000/api/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"username": "testuser", "name": "Test User", "password": "test1234"}'

# 웹사이트에서 호출 - 실패 (404 Not Found)
```

### 원인 분석

Docker Compose 환경에서 프론트엔드는 Nginx를 통해 정적 파일을 서빙하고, `/api/` 경로는 백엔드로 프록시합니다.

**frontend/nginx.conf**의 프록시 설정에 문제가 있었습니다:

```nginx
# 문제 코드 (nginx.conf:19-20)
location /api/ {
    proxy_pass http://backend_api/;  # 끝에 / 있음 - 문제!
    ...
}
```

Nginx의 `proxy_pass` 동작:
- `proxy_pass http://backend_api/;` (trailing slash 있음)
  - 요청: `/api/auth/signup`
  - 프록시 결과: `http://backend_api/auth/signup` (**`/api` 제거됨**)

- `proxy_pass http://backend_api;` (trailing slash 없음)
  - 요청: `/api/auth/signup`
  - 프록시 결과: `http://backend_api/api/auth/signup` (✓ **경로 유지됨**)

백엔드는 `/api/auth/signup`을 기대하는데, 실제로는 `/auth/signup`으로 전달되어 404가 발생했습니다.

### 해결 방법

**frontend/nginx.conf**의 proxy_pass에서 trailing slash를 제거했습니다:

```nginx
# 수정된 코드 (nginx.conf:19-20)
location /api/ {
    proxy_pass http://backend_api;  # trailing slash 제거
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

프론트엔드 컨테이너를 재시작합니다:

```bash
docker-compose restart frontend
```

또는 nginx 설정이 빌드 시 복사되므로, 확실하게 적용하려면 rebuild:

```bash
docker-compose up -d --build frontend
```

### Nginx proxy_pass의 Trailing Slash 규칙

| proxy_pass 설정 | 요청 경로 | 프록시 결과 |
|----------------|----------|-----------|
| `http://backend/` | `/api/auth/signup` | `http://backend/auth/signup` (location 경로 제거) |
| `http://backend` | `/api/auth/signup` | `http://backend/api/auth/signup` (location 경로 유지) |

**핵심**: trailing slash가 있으면 location 경로가 제거되고, 없으면 전체 경로가 유지됩니다.

### 교훈

- Nginx의 `proxy_pass`에서 trailing slash는 경로 변환 동작을 완전히 바꿉니다
- Docker Compose 환경에서는 프론트엔드-백엔드 간 통신 경로를 주의 깊게 설정해야 합니다
- 로컬 개발 환경(Vite dev server)과 프로덕션 환경(Nginx)의 프록시 동작이 다를 수 있으므로 둘 다 테스트 필요

## 결론

회원가입 로직에서 발생한 세 가지 주요 문제를 해결했습니다:

1. **응답 스키마 문제**: `UserResponse` 스키마를 생성하여 회원가입 시 불필요한 관계 필드를 제거하고 성능을 개선했습니다. 이는 RESTful API 설계의 모범 사례인 "각 엔드포인트는 필요한 데이터만 반환"하는 원칙을 따릅니다.

2. **API 경로 불일치 문제**: 백엔드 라우터에 `/api` prefix를 추가하여 프론트엔드와 백엔드 간의 경로를 일치시켰습니다.

3. **Nginx 프록시 설정 오류**: `proxy_pass`의 trailing slash를 제거하여 프록시 경로가 올바르게 전달되도록 수정했습니다.

이제 회원가입 기능이 로컬 개발 환경과 Docker 프로덕션 환경 모두에서 정상적으로 작동하며, 프론트엔드에서 백엔드로의 모든 인증 관련 요청이 올바른 경로로 전달됩니다.
